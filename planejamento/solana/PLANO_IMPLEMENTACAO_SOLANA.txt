 - Devnet: só com autorização explícita e separada. Mainnet: fora deste plano.

 1. O QUE A SOLANA RESOLVE NO GIRO (e o que NÃO resolve)
--------------------------------------------------------------------------------

 Do documento do projeto:
   "A blockchain não é necessária para a planilha financeira de Maria. Ela passa
    a ter valor quando Maria e João precisam compartilhar uma regra e uma prova
    sem depender exclusivamente da palavra de um deles ou da própria GIRO."

 Portanto, na rede ficam SÓ quatro coisas:
   1. O ACORDO (regra aceita pelas duas carteiras): valor original, quanto já foi
      quitado, saldo restante, % das vendas, prioridade, prazo, situação.
   2. A EXECUÇÃO: numa venda paga com token, UMA transação divide o valor entre
      fornecedor(es), comissão e vendedor, e atualiza o saldo do acordo.
   3. O PAGAMENTO EM DINHEIRO CONFIRMADO PELAS DUAS PARTES: registro assinado
      pelo vendedor E pelo fornecedor (a confirmação que hoje é por link local).
   4. A PROVA DE CONCLUSÃO: attestation (SAS) com a impressão digital do
      comprovante que já geramos em src/domain/proof.ts.

 Fica FORA da rede (continua no SQLite local): contatos, nomes, telefones,
 caixa físico, contas e metas pessoais (Organizar), equipe e diárias, histórico
 detalhado, importação de documentos, preferências.

 O GIRO NÃO guarda dinheiro (não custodial): o token vai direto da carteira do
 cliente para as carteiras de destino na mesma transação.

 2. ARQUITETURA ESCOLHIDA (e por quê)
--------------------------------------------------------------------------------

 2.1 Híbrido "local primeiro, rede como prova"
   - O SQLite continua sendo a fonte da experiência do vendedor (rápido, offline,
     com dados pessoais protegidos).
   - Cada evento que a rede precisa conhecer vira um item de "fila de envio"
     local (outbox) com estado: pendente → enviado → confirmado | falhou.
   - Um reconciliador compara ledgerSnapshot() (src/domain/integration.ts) com
     as contas on-chain e aponta divergências. Nada é sobrescrito sozinho.
   Por quê: se a rede local cair ou ainda não estiver instalada, o GIRO continua
   funcionando; a prova é adicionada quando a rede confirma.

 2.2 Programa Anchor próprio: "giro_acordos"
   Ferramentas (pesquisadas em out/2026): Anchor 1.x (1.2.0 é a versão
   verificada atual), cliente TypeScript gerado com Codama para @solana/kit,
   testes com LiteSVM (padrão do Anchor 1.x) + solana-test-validator/Surfpool
   para integração.

 2.3 Token de teste local
   - Mint SPL "BRL-T" (2 casas decimais: 1 unidade = 1 centavo, igual ao GIRO,
     que já trabalha em centavos inteiros).
   - Criado só no validador local; distribuído para carteiras de teste.
   - Usar token_interface (funciona com Token e Token-2022).

 2.4 Assinaturas
   - Produção (futuro): cada pessoa assina na própria carteira (Phantom,
     Solflare… via Wallet Standard). O GIRO nunca guarda chave de ninguém.
   - Fase local: carteiras de teste (solana-keygen) guardadas em pasta ignorada,
     usadas pelo servidor local SÓ para simular Maria, João, Pedro e o cliente
     na demonstração. Isso deve ser dito com transparência na banca.

 2.5 Solana Pay (transaction request)
   - GET  /api/solana-pay/:cobranca  → { label, icon }
   - POST /api/solana-pay/:cobranca  { account } → { transaction, message }
     A transação contém a instrução settle_sale do programa + uma "reference"
     (chave pública aleatória, somente leitura) para localizar e validar o
     pagamento depois (findReference / validação no servidor).
   - Limitação local: celular de verdade não alcança 127.0.0.1. Na fase local o
     pagamento é feito por uma carteira de teste no próprio PC. Expor para celular
     exigiria URL pública/túnel = serviço externo = autorização.

 2.6 Attestation (SAS — Solana Attestation Service)
   - Programa oficial: 22zoJMtdu4tQc2PzL74ZUT7FrwgB1Udec8DdW4yw4BdG
   - Hierarquia: Credential (emissor + assinantes) → Schema (formato) →
     Attestation (registro, com nonce e validade opcional; expiry 0 = não expira).
   - SDK TypeScript: @solana/attestation (cliente oficial); guias da comunidade
     usam sas-lib + gill. Rust: crate solana-attestation.
   - Local: compilar o SAS a partir do código-fonte e carregar no validador com
       solana-test-validator --reset --bpf-program 22zoJMtdu4tQc2PzL74ZUT7FrwgB1Udec8DdW4yw4BdG sas.so
     ("solana program dump" do mainnet também funciona, mas lê de RPC externo →
     precisa de autorização).
   - Schema "giro-acordo-concluido-v1", campos:
       agreement_key   [u8;32]  hash do código do acordo (já calculado hoje)
       record_hash     [u8;32]  SHA-256 do comprovante (src/domain/proof.ts)
       completed_at    i64
       on_time         bool
     Sem nomes e sem valores (os valores ficam no arquivo do histórico; a rede só
     confirma que aquele arquivo bate com o que foi atestado).
   - Quem emite: credential "GIRO" com assinante = chave emissora do GIRO.
     Para reduzir a dependência do GIRO, o attestation aponta o agreement_key;
     qualquer pessoa pode conferir na conta do acordo (assinada pelas duas
     carteiras) que ele está "Concluído".

 3. PROGRAMA "giro_acordos" — CONTAS, INSTRUÇÕES E REGRAS
--------------------------------------------------------------------------------

 3.1 Contas (PDAs)
   SellerState   seeds ["seller", vendedor]
     vendedor: Pubkey · committed_bps: u16 (soma dos % ativos+pendentes ≤ 10000)
     active_count: u8 · bump
   Agreement     seeds ["agreement", vendedor, agreement_key]
     vendedor, fornecedor: Pubkey · mint: Pubkey · agreement_key: [u8;32]
     original, paid: u64 (centavos) · rate_bps: u16 · priority: u16
     due_ts: i64 · status: Proposed | Active | Completed | Rejected | Cancelled
     version: u32 · created_ts, completed_ts: i64 · pending_change: Option<Terms>
     bump
   OffchainPayment seeds ["cash", agreement, nonce]   (pagamento em dinheiro)
     amount: u64 · paid_ts: i64 · assinado por vendedor E fornecedor

 3.2 Instruções
   propose(terms)            assina: vendedor     → status Proposed
   accept()                  assina: fornecedor   → Active (checa capacidade)
   reject()                  assina: fornecedor   → Rejected (fecha e devolve aluguel)
   propose_change(terms)     assina: qualquer parte → guarda pending_change
   decide_change(aceita?)    assina: a OUTRA parte → aplica ou descarta; version+1
   settle_sale(amount, commissions[])
       assina: cliente (dono da conta de token de origem)
       contas fixas: vendedor, mint, conta do cliente, conta do vendedor,
                     token_program, seller_state
       remaining_accounts: pares (Agreement PDA, conta de token do fornecedor)
                           ordenados por prioridade; + contas dos comissionados
       efeito: transfer_checked para cada destino e paid += parte; o resto vai
               para o vendedor; Completed quando paid == original; emite eventos.
   record_offchain_payment(amount, nonce)
       assina: vendedor E fornecedor → paid += amount (nunca acima do restante)
   cancel_proposal()         assina: vendedor, só antes do aceite

 3.3 Regra de divisão (IDÊNTICA ao motor atual em src/domain/finance.ts)
   1. valores fixos por venda; 2. comissões percentuais; 3. acordos por
   prioridade (menor número primeiro), depois data de criação, depois id;
   4. o que sobra é do vendedor.
   parte = min( floor(valor × bps / 10000), restante_do_acordo, ainda_disponível )
   - Nunca destina mais do que falta (ex.: faltam R$ 3 → transfere R$ 3, conclui).
   - Soma dos % aceitos ≤ 100% (checado em accept com SellerState).
   - Aritmética só com checked_add/checked_sub/checked_mul (u128 no meio).

 3.4 Limites técnicos a respeitar
   - Transação ≈ 1232 bytes / limite de contas: na v1 limitar a, por exemplo,
     4 acordos ativos + 2 comissionados por venda; acima disso usar Address
     Lookup Tables (v2).
   - Pedir compute budget explícito em settle_sale e medir nos testes.
   - Contas de token de destino: criar ATA de forma idempotente antes (no cliente).

 3.5 Segurança (checklist mínimo)
   - Account<'info, T> e Signer<'info> em tudo; UncheckedAccount só com /// CHECK.
   - Validar seeds/bump de cada Agreement recebido em remaining_accounts, e que
     agreement.vendedor == vendedor da venda e agreement.mint == mint.
   - Validar dono da conta de token do fornecedor == agreement.fornecedor.
   - has_one / constraints para status (só Active recebe parte da venda).
   - Testes negativos para cada regra (assinatura errada, conta trocada, PDA
     falso, overflow, acordo concluído, venda com valor zero).
   - Autoridade de upgrade do programa: chave local; em rede pública, multisig
     (fora deste plano).

 4. COMO O GIRO ATUAL SE LIGA À SOLANA (mapa)
--------------------------------------------------------------------------------

   GIRO hoje (local)                         Solana (fase local)
   ----------------------------------------- ------------------------------------
   Convite + aceite (link local)             propose + accept (2 carteiras)
   Pedido de mudança / decisão               propose_change + decide_change
   Venda digital "simulada"                  settle_sale via Solana Pay (BRL-T)
   Venda em dinheiro + entrega + confirmação record_offchain_payment (2 assinaturas)
   Comprovante (SHA-256, proof.ts)           attestation SAS "giro-acordo-concluido-v1"
   ledgerSnapshot() / attestationPayloads()  contas Agreement / attestations
   Verificar histórico recebido (arquivo)    + consulta on-chain dos códigos

 Novos módulos no projeto (propostos):
   solana/                      workspace Anchor (programs/giro_acordos, tests)
   solana/clients/giro/         cliente TS gerado pelo Codama (não editar à mão)
   server/chain/                adaptador: outbox, envio, reconciliação
   server/chain/wallets/        carteiras de TESTE (ignoradas; nunca versionar)
   tests/chain-*.test.ts        testes que só rodam com GIRO_SOLANA_CLUSTER=localnet

 Na tela do vendedor: nenhum jargão. Só um selo discreto "Registrado ✓" no
 acordo e no comprovante quando a rede local confirmar (regra 14).
